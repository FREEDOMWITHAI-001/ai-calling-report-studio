a local SQLite file at backend\data\app.db - no server needed.

 3. WHAT THE APP DOES
-------------------------------------------------------------------------------
UPLOAD DATA
  Drop in any CSV or XLSX. The app:
    - lists every sheet in the workbook
    - previews the first rows
    - auto-detects the data type (registration / AI calling / sales / attendance
      / platform daily / custom) and the column mapping
    - lets you correct both before loading
    - saves the mapping as a reusable template keyed on the file's header
      signature, so the same export is one click next time
  Everything is logged in raw_uploads with rows / inserted / skipped / status /
  first error. Re-uploading the SAME file inserts nothing (each row carries a
  content hash), but a genuine repeat registration is still stored.

DATA
  Browse the normalized tables the reports are built from.

REPORTS
  - date range, plus presets (last 7 / 14 / 30 days, this month)
  - filter by language/segment and by specific bot names  (both honoured NOW)
  - tick PDF / Excel / PowerPoint - generates all chosen formats in one action
  - "Preview numbers" shows the entire report on screen before exporting
  - batch generation for several windows at once (POST /api/reports/batch)
  - every generated file is stored with its metadata and can be re-downloaded
    without recomputing

METHODOLOGY (settings page)
  Every constant is editable and saved as a named config, and is stamped into
  each generated report:
    sale value (Rs 6,999), cost per minute (Rs 5.10), connect threshold (15s),
    billing rounding (ceil_minute / exact_second), baseline mode, uplift mode
    (weighted / simple), lead-age band edges, team/test patterns, bot role
    patterns, attendance match mode.
  Bot roles (signup / day_of / other) can be changed per bot.

 5. HOW THE REPORT IS CALCULATED
-------------------------------------------------------------------------------
 1. Registrants = rows in the window, team/test rows removed, deduplicated to
    people (phone -> email -> name).
 2. Connected  = a signup or day-of bot held a conversation LONGER than 15s.
    Signup / day-of / both groups overlap by design.
    Baseline    = everyone the bots never got talking to (never dialled +
                  dialled but no answer, merged).
 3. Show-up    = per-person match against the attendance data.
 4. Buyers     = per-person match against sales; ONE full Rs 6,999 sale per
    person (lock + balance collapse to one); rows dated before the person
    registered are dropped; zero-amount rows are dropped.
 5. Extra sales credited to AI = registrants split into lead-age bands
    (0-2, 3-6, 7-9, 10-13, 14+ days). Inside each band connected leads are
    compared ONLY with baseline leads of the same age; the band's buy-rate gap
    is multiplied by that band's connected count; the bands are summed.
    This is like-for-like weighting, not a raw comparison of two different mixes.
 6. Talk cost = in-scope bots only, calls with talk time only, each call rounded
    UP to the next whole minute (billing is per minute) x Rs 5.10.
 7. Revenue with AI = buyers x Rs 6,999
    AI added         = extra sales x Rs 6,999
    Revenue without  = with - added
    ROI              = added / talk cost
    Significance     = two-proportion z-test (connected vs baseline).

Each report also carries an audit block: rows in/out, repeats and team rows
removed, sale rows dropped and why, call match rate, exact vs billed minutes,
and the observational caveat.

 6. DATA MODEL
-------------------------------------------------------------------------------
  clients, events, bots        who / which workshop / which bot (role)
  persons                      one row per human, resolved across every file
  registrations                sign-ups: name, email, phone, date/time, UTM,
                               language, program
  ai_calls                     one row per call: bot, contact, status, outcome,
                               sentiment, interest, duration, turns, timestamps,
                               recording url, call sid
  sales                        amount, date, payment id/status/type, product
  attendance                   zoom/webinar attendance + minutes in session
  webinar_daily                platform's own daily counts (reconciliation only)
  generic_datasets/records     any new data type - stored as JSON, still linked
                               to a person
  raw_uploads                  upload audit log
  mapping_templates            remembered column mappings
  methodology_configs          saved calculation settings
  report_runs                  every generated report + file paths

Join key across datasets: phone number normalized to the last 10 digits.
Email is the second key, name the third - and name is ONLY trusted when the row
has no usable phone (which is exactly the attendance export's case: "Not Found"
numbers and platform alias emails). This rule matters: trusting name when a
phone is present merged different people who share a common name and cost ~100
registrants in an early run.

All tables carry created_at / updated_at.

10. KNOWN GAPS  (full list in README.md)
-------------------------------------------------------------------------------
 1. BIGGEST ONE: the supplied call log only covers ~17 Jul onward. The
    26 Jun - 17 Jul 2026 report therefore cannot be fully reproduced -
    registrants (2,047 vs 2,056) and show-up (1,018 vs 1,018) match, but talk
    cost lands at Rs 3,172 instead of Rs 12,337 because ~2,300 calls and the
    entire day-of bot are missing from that period.
    FIX: upload the older call log via the Upload page. No code change needed.
 2. Report 2's methodology is the default (not-connected baseline + lead-age
    weighting). Report 1's simpler variant is available by switching
    baseline_mode / uplift_mode under Methodology.
 3. Report 2's Overview tab mentions a weighted-band table that is not actually
    on that tab. This app renders it, which is what the method text describes.
 4. No authentication (as requested). Binds to 127.0.0.1 - anyone who can reach
    the port can read uploaded PII.
 5. Background work uses FastAPI background tasks, not Celery. A 20 MB call log
    ingests in ~45s and a report renders in under a second, so a broker is not
    yet worth it. Both entry points are isolated functions, so moving to Celery
    later is a drop-in change.
 6. Nothing is deleted automatically. Uploads: backend\data\uploads.
    Reports: backend\data\reports. Both have DELETE endpoints.
 7. The UI was never visually confirmed in a browser during the build - the
    Chrome extension did not respond. The build compiles and the API serves it.
